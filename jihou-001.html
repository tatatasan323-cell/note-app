八割削除

指示を足す時代から、削る時代へ

特報

Anthropic は 7月24日、最新モデル Claude Opus 5 の公開に合わせ、 Claude Code の内部指示（システムプロンプト）を八割以上削除したと公表した。 削ったのに、コーディング性能の評価に測定可能な低下はなかったという。

同社が同日公開した記事「Claude 5 世代モデルにおけるコンテキスト・エンジニアリングの新しい規則」は、 その理由をこう説明する。かつて書かれた大量の指示は、モデルの失敗を防ぐための足かせだった。 Claude 5 世代はその失敗をしなくなったため、足かせは効果を失い、 いまや互いに矛盾する指示と、無駄なトークン消費だけが残っている ── と。

つまり今回のニュースは「新しい書き方を覚えろ」ではない。持っている指示書を減らせ、である。 Claude Code に指示書を書き溜めてきた人ほど、いま損をしている可能性が高い。

要 保 存

編集・要約：Claude（Opus 5）／ 発行：AI内製化工房 MITA

SECTION 01

六つの転換

公式ブログが挙げた、書き方の切り替えどころ

Anthropic はこの削除作業から得た知見を、六つの「転換」として整理している。 いずれも共通しているのは、モデルを縛るのをやめ、モデルが判断できる材料を渡す側に回るという方向である。

表1 ─ 公式ブログが示した六つの転換
#これまでこれから具体例
1ルールを与える判断を委ねる 「コメントは書くな」→「周囲のコードと同じコメント密度で書け」
2使用例を並べる道具の設計で語らせる 例文を積むより、ツールの引数名や選択肢そのものを分かる形にする
3全部を前置きする必要な時に開く レビュー手順などは本体から出し、独立した Skill として必要時に読み込む
4大事なことは何度も書く道具の説明文に一度だけ システムプロンプトとツール定義に同じ注意書きを重複させない
5CLAUDE.md に手で書き溜める自動記憶にまかせる 関連する記憶を Claude 側が自動保存する仕組みへ移行
6素朴な仕様書濃い参照物 文章での説明より、コード・テスト・成果物そのもの・採点基準を渡す

五番目の「自動記憶」については、公開直後から制御を手放すことになるという反発も出ている。 本紙の見立てでは、手書きの記憶をすべて捨てる必要はない。捨てるべきなのは 「書いておかないと間違えるから書いた」種類の記憶であって、 「本人にしか分からない事実」は依然として手で書く価値がある。

SECTION 02

Opus 5 と Fable 5、それぞれの癖

同じ「Claude 5」でも、手綱の握り方は違う

Claude Opus 5 ── 放っておくと、よく喋り、よく広げる

削るべき指示

「最後に検証工程を入れよ」「サブエージェントで確認せよ」といった検算の指示は削除する。 Opus 5 は言われなくても自分の仕事を検証するため、指示を残すと二重に検算してトークンを浪費する。 「もう一度確認してから答えよ」の類も同じ理由で不要。

コードレビューでの「重大な問題だけ報告せよ」も逆効果になる。 指示に忠実に従って報告が減るため、全部出させて、絞るのは別工程にするのが公式の推奨である。

足すべき指示

逆に、この世代で必要になったのは短くしろと広げるなの二つ。 Opus 5 は返答が長く、作業中の実況も多い。冗長さは effort（思考量）を下げても縮まないので、 「簡潔に。前置きと注意書きは短く」と明示的に言葉で頼む必要がある。

スコープ拡大も癖の一つで、頼んでいない改善まで手を出しがちになる。 「頼まれた範囲を、頼まれた粒度でやれ」を一文入れておく。 サブエージェントも自発的に増やすため、小さい仕事では使うな・数は絞れと上限を示すとコストが安定する。

Claude Fable 5 ── 結果を渡して、任せる

手順書を渡してはいけない

Fable 5 は「人が数時間から数日、数週間かけて終える仕事」を丸ごと引き受ける設計になっている。 一手ずつ操縦する前提のプロンプトはこのモデルを持て余す。 公式の言い方を借りれば、欲しい結果を手渡し、道筋は本人に立てさせる。

従来モデル向けに作り込んだ Skill は「細かすぎて逆に品質を落とす」とまで書かれている。 移行時はまず素の状態で試し、それより良くならない指示は消す。

長時間運転ならではの備え

一回の応答が数分、自律実行なら数時間に及ぶ。タイムアウトと進捗表示の設計を先に直しておく。

長時間走らせる時に効くのが進捗の裏取り指示である。 「報告する前に、その主張がこのセッションのツール実行結果で裏づけられるか確認せよ」と入れると、 Anthropic の試験では作り話の進捗報告がほぼ消えたという。

もう一つが記憶の置き場。マークダウン一枚でよいので「前回の教訓を書き残す場所」を与えると、 このモデルは特に良く働く。指示書に書ききれない「前回こうして失敗した」を溜める場所を、 AIの側に一つ持たせておく ── それだけで効く、という話である。

おことわり ── これは Claude Code の話である

本紙が扱ったのは、Anthropic が自社の開発ツール Claude Code と、Claude 5 世代のモデルについて公表した内容である。 以下の「削れ」は、Claude Code を使う場合について言っている。

ChatGPT やその他のAI開発環境に、同じことがそのまま当てはまるかどうか ── 本紙は確かめていない。 各社が公表しているのは自社モデルの話であって、横に並べて「AI全般はこうだ」と言える材料は、いまのところない。 確かめていないことは、言わない。

工房が Claude Code を使っているから、その範囲で書く。それだけの話である。

SECTION 03

実践欄 ── 我々は、何を削るか

読んで終わりにしないための、六つの手順

  1. 一行ずつ「消したら間違えるか」を問う

    公式ドキュメントが示す唯一の判定基準がこれである。消しても Claude が間違えないなら、その行は消す。 指示書が長いと、本当に守ってほしい規則が埋もれて無視される ── これは推測ではなく、公式が明記している失敗パターンである。

  2. 「禁止」を「判断の軸」に書き換える

    禁則の列挙は、想定外の場面で効かないうえ、互いに衝突する。 「Xをするな・Yをするな」を並べるより、何を優先して判断するかを一文で示すほうが、この世代には効く。

  3. 常時ロードから、必要時ロードへ移す

    その作業をする時にしか要らない細則 ── レビューの観点、リリース手順、特定フレームワークの作法 ── は CLAUDE.md から出して Skill に移す。常駐させるのは、いつでも当てはまることだけ。

  4. 検証の二重指示をやめる

    「確認してから答えよ」「検算せよ」は、Opus 5 では削除対象である。 代わりに置くべきは、Claude 自身が回せる検証手段（テスト、ビルド、スクリーンショット比較）である。指示ではなく、装置で担保する。

  5. 公式の点検コマンドを一度通す

    Anthropic はこの一連の知見を claude doctor に組み込み、Skill と CLAUDE.md を適正サイズに直す用途に使えるとしている。 ターミナルから実行するコマンドで、まず現状診断として一度かけてみる価値がある。

  6. ここまでを、定期業務にする

    モデルは数か月単位で変わる。年に一度の見直しでは、去年の工夫を1年間背負い続けることになる。 月に一度、遅くとも四半期に一度。棚卸しそのものをAIに頼めるので、手間は数十分で済む。 情報を集め、いまのモデルで確かめ、環境を片づける ── これを暦に載せてしまう。

削除の実例 ── あなたの指示書にあてはめると

おそらく削れる（モデルが既にやる）

  • 「検算せよ」「二重に確認せよ」の類
  • コメントの書き方の細則
  • 「不確実なら不確実と言え」
  • 「丁寧に」「品質を高く」の一般論
  • 禁止事項の網羅的な列挙

※ 現行モデルの標準的な振る舞いに、すでに含まれている領域。

残すべき（あなたにしか書けない）

  • この仕事が何のためにあるか、という目的
  • 社内規程・契約に由来する外部制約
  • 触ってはいけないファイル・領域の線引き
  • 過去に実際に事故った、具体的な落とし穴
  • 開発環境の癖（必要な環境変数・ビルドの罠）

※ コードにも履歴にも書いていない事実は、モデルには推測できない。

用語解説

システムプロンプト
会話が始まる前に読み込まれる、AIへの常駐指示。Claude Code の場合はツールの使い方や振る舞いの規範が入っている。ユーザーからは見えないが、容量は確実に消費する。
effort（エフォート）
思考にどれだけ手間をかけるかの設定。low / medium / high / xhigh の四段階。費用と待ち時間を決める主要なつまみで、返答の長さは調整しない点に注意。
逐次開示（progressive disclosure）
すべてを最初に読ませず、必要になった時点で該当分だけ読み込ませる設計。Skill はこの仕組みの実体である。
Skill（スキル）
SKILL.md という説明書を持つフォルダ。関連する作業の時だけ自動で読み込まれる。「たまにしか要らない知識」の置き場所。
サブエージェント
別の文脈で並行して働かせる補助AI。本体の作業領域を汚さずに調査できるが、小さな仕事に使うと費用と時間が増えるだけになる。
社説 ── 削るのも、内製化の仕事である

本紙はこれまで、プロンプトの細かな技法を扱ってこなかった。扱ってきたのは、 「AIに迎合させないための5箇条」のような、短い憲章を一枚だけ手元に置く ── その程度の話である。 あとは使い込みながら、自社の価値観と判断軸を足して育てていけばいい、とも書いた。

今回のニュースは、その軽さが結果として正しかったことを示している。 だが同時に、宿題も残した。5箇条は、使っているうちに10箇条になり、20箇条になる。 増やす作業には達成感があり、減らす作業にはない。「育てろ」と言った以上、「削れ」も言わなければ無責任である。

そして、少なくとも Claude Code については、その棚卸しは年に一度では遅い。 モデルは数か月で変わり、去年の工夫が今年の足かせになる。 月に一度、遅くとも四半期に一度。それくらいの間隔で十分だし、それより空けると効かない。

面倒な作業ではない。この棚卸しそのものを、AIにやらせればいい。 「この指示書を、いまのモデルが標準でやることと照らして、消しても振る舞いが変わらない行を挙げてくれ」── 頼み方はそれだけである。集める、確かめる、片づける。環境の整理整頓は、AI内製化という仕事の一部である。
